# i18n Design (zh-CN / en-US)

## Goal

Add runtime language switching for the desktop app with **Simplified Chinese (`zh-CN`)** and **English (`en-US`)** as first-class locales. UI copy, product metadata labels, user-visible engine messages, and Ant Design component locale should follow the selected language. User-generated content (group names, member names, chat messages) is never translated.

## Non-Goals (First Pass)

- Translating LLM system prompts (deferred to a later phase; UI locale and prompt locale may diverge)
- Tauri window title localization
- Rust-side user-facing strings (currently negligible)
- Code comments / JSDoc translation
- Additional locales beyond `zh-CN` and `en-US`
- CI extraction of missing translation keys (follow-up tooling)

## Current State

- Stack: Tauri 2, React 19, Vite, antd 6, `@lobehub/ui`
- No i18n library; ~60 `.ts/.tsx` files contain hardcoded Chinese
- Hotspots: `CLIGroupSettings`, `cliEngine`, `agentEngine`, `CreateGroupWizard`, config modules (`groupProduct`, `tagTaxonomy`, `cliTasks`)
- `use-theme.ts` already implements `localStorage + system` preference — reuse the same pattern for locale

## Approach

Use **react-i18next + i18next** (recommended over custom `t()` or Lingui for this codebase size).

Reasons:

- Mature React hooks, namespaces, interpolation, pluralization
- Straightforward Ant Design `ConfigProvider locale` integration
- Lazy-loadable JSON resource files per namespace
- Incremental migration: untranslated keys fall back to `zh-CN`

## Architecture

```
localStorage('locale') + navigator.language
        ↓
useLocale / localeStore  →  resolved: 'zh-CN' | 'en-US'
        ↓
i18next (resources, fallbackLng: 'zh-CN')
        ↓
├── React components: useTranslation(ns).t(key)
├── Product config: labelKey / descriptionKey → t(key) at render
├── antd ConfigProvider locale (zhCN | enUS)
└── Date/sort: resolved locale instead of hardcoded 'zh-CN'
```

### Directory Layout

```
src/i18n/
  index.ts                 # init, resource registration, changeLanguage
  antdLocale.ts            # map resolved locale → antd locale object
  resources/
    zh-CN/
      common.json
      sidebar.json
      chat.json
      settings.json
      cli.json
      product.json
    en-US/
      (same namespaces)
src/hooks/use-locale.ts    # 'system' | 'zh-CN' | 'en-US', mirrors use-theme
```

### Locale Resolution

| Stored value | Resolved locale |
|---|---|
| `system` (default) | `navigator.language` starts with `zh` → `zh-CN`, else `en-US` |
| `zh-CN` | `zh-CN` |
| `en-US` | `en-US` |

Persist key: `locale` in `localStorage`.

### App Integration

Wrap the app in `I18nextProvider` and pass Ant Design locale via `ConfigProvider` from `antd` (separate from `@lobehub/ui`'s `ConfigProvider`):

```tsx
const { resolvedLocale } = useLocale();

<I18nextProvider i18n={i18n}>
  <AntdConfigProvider locale={getAntdLocale(resolvedLocale)}>
    <LobeConfigProvider ...>
      ...
    </LobeConfigProvider>
  </AntdConfigProvider>
</I18nextProvider>
```

On locale change: `i18n.changeLanguage(resolvedLocale)` + update `document.documentElement.lang`.

### Language Switcher UI

Add to Sidebar settings dropdown (alongside theme toggle):

- 跟随系统 / Follow system
- 简体中文
- English

## String Categories & Migration Rules

### 1. UI Components (migrate in Phases 1–4)

Replace hardcoded strings with `t('namespace.key')`.

```tsx
const { t } = useTranslation('cli');
<Button>{t('actions.run')}</Button>
```

Toast messages:

```tsx
toast.success(t('task.deleted', { name: task.title }));
```

### 2. Product Config (Phase 2)

Convert display fields to keys:

```ts
// Before
{ type: 'ai', label: '角色群', description: '...' }

// After
{ type: 'ai', labelKey: 'product.groupTypes.ai.label', descriptionKey: 'product.groupTypes.ai.description' }
```

Render sites resolve via `t(item.labelKey)`. Keep structural IDs (`type`, `id`, strategy enums) unchanged — they are not translated.

Files: `groupProduct.ts`, `tagTaxonomy.ts`, `providers.ts` (built-in labels), `cliTasks.ts` (user-visible labels).

### 3. Engine User-Visible Strings (Phase 5)

Errors and stage labels shown in the UI move to i18n. Engine modules must not import React hooks.

Options (pick one during implementation):

- Call `i18n.t()` directly from `src/i18n/index.ts` (no hook needed)
- Inject a `translate: TFunction` into engine entry points

Keep in i18n:

- `PIPELINE_STAGE_LABELS`, `REVIEW_STAGE_LABELS`, user-facing `throw new Error(...)` messages
- Agent display names like `协调者`, `裁判` when shown in UI

### 4. LLM Prompts (Deferred — Phase 6)

System prompts in `agentEngine.ts`, `cliEngine.ts` stay in Chinese until a dedicated prompt-locale layer exists (`prompts/zh-CN/`, `prompts/en-US/`). UI language switching must not silently change prompt language in the first pass.

## Key Replacements

| Location | Change |
|---|---|
| `prompt.ts` `toLocaleDateString('zh-CN')` | Use `resolvedLocale` |
| `CLITaskInfoPanel`, `CLITaskSidebar`, `CLIGroupSettings` `toLocaleString(undefined, …)` | Pass `resolvedLocale` |
| `ProviderLibrary.tsx` `localeCompare(..., 'zh-CN')` | Use `resolvedLocale` |

## Naming Conventions

- Keys: `namespace.section.camelCase`, e.g. `cli.settings.workspacePath`
- Namespaces map to feature areas: `common`, `sidebar`, `chat`, `settings`, `cli`, `product`
- Interpolation: `{{name}}`, `{{count}}`
- Default/fallback language: `zh-CN`

## Phased Rollout

### Phase 0 — Infrastructure

- Install `i18next`, `react-i18next`
- Create `src/i18n/`, `use-locale.ts`
- Wire `App.tsx` (i18n + antd locale)
- Language switcher in Sidebar
- Seed `common.json` (~15 keys) to validate end-to-end

**Done when:** switching language updates Ant Design internals (DatePicker empty text, Pagination, etc.) and at least one Sidebar label.

### Phase 1 — App Shell

- `Sidebar`, `Header`, `UserSection`, `Layout`
- Global toast strings in touched files
- `CreateGroupWizard` group-type selection step

### Phase 2 — Product Config

- `groupProduct.ts` → labelKey pattern
- `tagTaxonomy.ts`, built-in provider labels
- `AIMemberLibrary`, `ProviderLibrary`

### Phase 3 — Chat & Settings

- `ChatUI`, `AgentChatUI`
- `AIGroupSettings`, `AgentGroupSettings`
- `AIMemberEditor`, `ProviderEditor`, `MemberPicker`

### Phase 4 — CLI Module (largest)

- `CLIGroupSettings`, `CLITaskUI`, `CLITaskSidebar`
- `CLITaskInfoPanel`, `CLIRaceResultsDrawer`, `CLITemplateListPanel`
- `cliTasks.ts` user-visible labels

### Phase 5 — Engine User Strings

- User-visible errors and stage labels in `cliEngine.ts`, `agentEngine.ts`
- Use non-hook `i18n.t()` access

### Phase 6 (Optional) — Prompt Localization

- Separate prompt packs per locale
- Allow UI locale ≠ prompt locale

## Testing

- Add `src/i18n/resources.test.mjs`: assert every key in `zh-CN` exists in `en-US` (and vice versa) per namespace
- Existing unit tests unchanged unless they assert Chinese UI strings
- Manual: switch locale → verify Sidebar, wizard, one settings panel, one CLI panel, one toast

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Large diff touching many files | Strict phase boundaries; one PR per phase |
| Missing en-US keys at runtime | Fallback to `zh-CN`; symmetry test in Phase 0 |
| Engine importing React hooks | Ban hooks in engine; use standalone `i18n.t()` |
| Ant Design vs Lobe UI ConfigProvider nesting | Wrap antd locale outside Lobe provider; verify DatePicker/Pagination in both locales |
